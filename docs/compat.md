# Compatibility with TLC

This document defines in what sense tlx is "the same as TLC". tlx only promises **semantic
compatibility**: for the same spec and configuration it reaches the same verdict, the same state
space and equivalent counterexamples. Command line and output format are outside the contract.

- **Baseline**: TLC `2026.10.02.163556 (rev 1813307)` (`third_party/tla2tools.jar`). The jar is a
  **verified** artifact, not whatever a download URL serves today: `scripts/dependencies.py`
  (`TLA2TOOLS_PIN`) declares the pinned SHA-256, the git revision the manifest must report and the
  source URL; `scripts/fetch-deps.sh` installs only bytes that match and refuses an existing jar
  that does not; `scripts/tests/test_dependencies.py` checks the pin against the documents. The v1.8.0
  release asset has been re-uploaded with another revision, so the URL is a best-effort download
  source and the verification is the authority; the baseline is never upgraded implicitly (an
  upgrade is a deliberate change of the pin, with the measured differences recorded). Order of
  authority for semantics: TLC > tlx interpreter (`-interp`) > tlx compiled tier (the default tier;
  `TLX_PARANOID`).
- **Modes**: the contract below is the one of `-tlc` (TLC-compatible results). The default mode
  (without `-tlc`) may use optimizations TLC does not have that keep only tier 1 and the validity of
  counterexamples (a violation is reported exactly when one exists, with a genuine counterexample);
  counts, depth and which counterexample may then differ. Today the default mode applies a
  symmetry of sets of model values that tlx proves to runs that check only safety, and names it in
  an `Optimizations:` line ([usage.md](usage.md) section 6.3). The parity tests run with `-tlc`; the
  default mode is compared with TLC by verdict (`--default-mode` of spectest and difftest).
- **Must match**: sections 0 and 1. A difference is a bug and fails the tests (unless it is a
  documented difference D-n, marked `xfail` in the test).
- **Outside the contract**: section 2. tlx keeps its current output format (its own test scripts parse
  it) and may change it, but does not aim to align it with TLC.
- **Documented differences (D-n)**: differences with evidence, or things that cannot be compared (TLC's
  own randomness and races, features tlx lacks), section 3. Do not "chase" them; a new entry needs
  evidence (a reproducing spec, results of several TLC runs, or a TLC source location).
- **Known limitations**: section 5. How all of this is tested: section 4.

## 0. The three tiers

| Tier | Content | Requirement | How tests compare |
|---|---|---|---|
| **1: Verdict** | The kind of result (success / invariant violated / deadlock / action property violated / temporal property violated / ASSUME false / POSTCONDITION false / evaluation error); the names that are violated (invariants, action properties, initial-state properties, POSTCONDITION; for temporal properties at least one violated property name, and every reported name is really violated by the reported counterexample); whether a spec or configuration is accepted or rejected; error versus no error | **Must match exactly** (multi-worker same-level safety choices: D-3) | Exact; a difference is a bug |
| **2: State space** | Generated / distinct counts and depth; the length of safety counterexamples (BFS shortest); the semantics of TLA+ and of the modules (enumeration, `CHOOSE`, comparison and equality, lazy evaluation, `ENABLED`, SYMMETRY/VIEW fingerprint semantics, return values and error conditions of native standard and community module operators) | **Must match exactly** (model checking is defined at `-workers 1`, see D-3) | Exact |
| **3: Incidental choices** | Which of several equally short safety counterexamples is reported; the exact shape and start of a liveness lasso; the class of an error and the exit code (only "it fails" has to agree); the order of run-time strings (only when it affects tier 2); print order and the line order of `Print` (several workers); statistics such as branching numbers; which valid safety violation (kind/name and trace) at the same BFS level is reported with several workers, and counts, search depth and safety-trace length at a multi-worker early stop (D-3) | **Only has to be valid**: a counterexample must be a legal behavior of the spec that really violates the reported property (checked by TLC; modulo VIEW under VIEW, see D-10); everything else only must not affect tiers 1 and 2 | Not compared exactly; if a counterexample differs from TLC's, TLC validates it (trace spec) |

The authoritative model-checking oracle is **TLC `-workers 1`**. With several
workers, TLC and tlx may report different valid safety violations at the same
BFS level (including an invariant versus an action property). This choice of
violation kind/name and trace is tier 3; the counterexample must really violate
the reported property. Single-worker verdicts and names remain exact (D-3).
In particular,
`SYMMETRY` is a promise made by the model: if its transition relation is not
equivariant under the declared permutations (for example Neon `MaxVoteAcc`
chooses the smallest acceptor), representative selection can change the explored
graph with the worker schedule. Such models use `oracle_workers: 1` and
`asymmetric_symmetry: true` in the external manifest. Single-worker counts and
depth remain exact; multi-worker counts/depth only have to be valid (D-22).
Liveness-failure counts and depth are also timing-dependent: TLC can stop at a
periodic liveness check before the graph is exhausted, while tlx checks offline.
These statistics are not exact comparison fields, even with one worker.

Parts of tier 3 that already agree with TLC (the lasso construction, error classes, string order) are
kept, but no new alignment work is done for tier 3. Entries in section 1 that belong to tier 3
(the exact state sequence of a counterexample, the error class) are to be read that way.

**TLC and SANY defects are not copied.** When TLC or SANY behave in a clearly defective way (for
example SANY's `RECURSIVE` arity check only looks at the last parameter; TLC's comparison of a
record with a non-record function reports an error or FALSE depending on which one is the receiver),
tlx implements the correct TLA+ semantics instead. Each case is a D entry in section 3 (D-17, D-18)
and is noted in the expected result of the test. Calling something a defect needs grounds (the
language definition, an asymmetry of the same behavior, or dependence on internal ordering).

## 1. What must match

Conditions: the same spec, the same cfg, the same mode and parameters (`-deadlock`, `num` and
`-depth` of `-simulate`/`-generate`, ...); model checking (BFS) is defined at `-workers 1` (several
workers: D-3); simulation: D-2.

| Item | Definition |
|---|---|
| Verdict | Success / invariant violated (in an initial state or along a behavior) / deadlock / action property violated / temporal property violated (including a PROPERTY violated by an initial state) / ASSUME false / POSTCONDITION false / evaluation error (including `Assert` failure) / spec or configuration rejected |
| Names violated | The names of the violated invariants, action properties, initial-state properties and POSTCONDITION; for a temporal violation **all** properties the counterexample violates (TLC attributes violations to the lasso after the fact) |
| Counts | Generated / distinct (and states left on the queue): on success, and when a violation or evaluation error occurs; for simulation, generated only for specs whose behaviors do not depend on random choices (`# deterministic` in the tests) |
| Depth | The depth of the state graph search |
| Counterexample | The state sequence and its order (under BFS the shortest path as TLC selects it from its successor generation order); the action of every step (label and location); the back-edge position or stuttering of a lasso; the state of an initial-state violation or initial-state evaluation error. States are compared **by value** (the line wrapping of long values is not compared) |
| TLA+ semantics | TLC's interpretation of TLA+: enumeration order, `CHOOSE`, comparison and equality of values (including type errors across types), lazy evaluation rules, action splitting and `UNCHANGED`, `ENABLED`, fingerprint semantics under SYMMETRY/VIEW, CONSTRAINT/ACTION_CONSTRAINT, TLCGet/TLCSet, cfg overrides, ... (details in [tlc-semantics.md](tlc-semantics.md)) |
| Module semantics | Operators of the standard modules (Naturals, Integers, Sequences, FiniteSets, Bags, TLC, Reals, ...) and of the CommunityModules that TLC implements natively: same return values and error conditions |

The **kind** of an evaluation error (division by zero, overflow, `Assert`, out of domain, ...) is part
of the semantics: tlx and TLC fail at the same place; the wording is not part of the contract. The
error **class** (spec rejected / configuration rejected / evaluation error / `Assert` failure, i.e.
the exit code: TLC's 150 parse, 151 configuration, 75 evaluation, 14 Assert, 255 other) is tier 3
(section 0): agreement that exists is kept, and the tests only compare that the run fails (spectest
no longer compares exit codes).

On macOS and Linux, recursion that reaches a native stack guard page also prints the
depth guard's stack-overflow explanation and exits with evaluation-error status 75.
This fallback runs on an alternate signal stack and terminates immediately without
unwinding or printing a state trace; other memory faults retain their default signal
behavior. It covers the main thread and all threads created by tlx, including native
build threads. Registration supports up to 4096 simultaneous protected threads and
fails explicitly if that capacity is exhausted. The usual recursion guards still
report recoverable evaluation errors before the native stack fills.

## 2. Outside the contract

The following may differ; whether to change them is tlx's own decision (tlx's script
`scripts/tlc.py parse()` parses tlx's output, so changing the format means changing it too):

- names and syntax of command-line options;
- configuration syntax extensions: tlx accepts signed integers in constant assignments
  (`CONSTANT C = -1` and `CONSTANT C = {-1, 0}`). TLC's `tlc2.tool.impl.ModelConfig.parseValue`
  has no unary-minus production and rejects both; its fallback consumes `-` as a model
  value and leaves the numeral as an unexpected token. This is a configuration-format
  limitation, not a TLA+ semantic defect. The same values can be supplied to TLC through
  a definition override (`CONSTANT C <- Negative`, with `Negative == -1` in the module);
- text, order and position of messages, message codes and levels of `-tool`, warnings;
- the format of progress and statistics lines, the contents of the version and mode lines;
- exit codes (except the error classes of section 1);
- the layout of printed values (TLC prints values that are too wide over several indented lines,
  tlx prints them on one line);
- the output and error texts of the front end (SANY), but whether a spec is **accepted or
  rejected** must match (`scripts/sanydiff.py`; zero differences on the corpus).

## 4. How compatibility is checked

Commands, comparison rules and expected failures are defined by [testing.md](testing.md): spec tests
compare by the three tiers of section 0 and let TLC validate counterexamples that differ
(testing.md section 5); corpus differential tests compare verdict, counts and depth (testing.md section 6); the
front end is compared with SANY on acceptance/rejection (testing.md section 9); the compiled tier (the default tier) is compared
with the interpreter (`-interp`) state by state under `TLX_PARANOID` (testing.md section 8);
`crates/tlx-cli/tests/output.rs` is a regression test of tlx's own output format (not part of the contract).

`tests/specs/K*` cover this contract: K1 action property violation (counterexample), K2 BFS deadlock
(shortest counterexample), K3 ASSUME false, K4 one counterexample violating two temporal properties,
K5 invariant counterexample in a branching graph, K6 `Assert` failure in an action (counterexample),
K7 counterexample with long values (compared by value), K8-K12 configuration problems and their
**class** (exit code): unassigned constant, undefined INVARIANT, missing NEXT (initial states are computed
first, then 2115 is reported), superfluous CONSTANT in the cfg, missing INIT. `EC*` are the rules of
`<-` replacement in the cfg (undefined right side 2224, left side not in the spec 2226, left side a
definition missing from the module 2226, different parameter counts 2225, unknown module name 2245,
right side itself replaced 2223). `CC*` are boundaries of the configuration rules (CC1: assignments in
the cfg only act on constants and definitions visible in the root module; any other name -
undeclared, a VARIABLE, a definition only in an INSTANCE module, an unknown `[M]` module - is silently
ignored). `FS1`-`FS4` cover the fold operators of CommunityModules that TLC overrides in Java
(`FoldSet`, `FoldFunction`/`FoldFunctionOnSet`, `FoldSeq`, `FoldLeft`/`FoldRight`/`...Domain`): FS1 pins the
fold order (TLC's normalized order, `acc = op(x, acc)`; `*Left` is `op(acc, x)`) and the values,
FS2-FS4 the error conditions when the argument is not a set / function / sequence (FS2: D-7).

## 5. Known limitations

This is the single source for known limitations ([design.md](design.md) and
[usage.md](usage.md) link here). The operator-by-operator support of TLC options and modules is in
[features.md](features.md).

- **Language**: real numbers are not supported (as in TLC, `Reals` only has placeholder
  definitions: real literals are rejected at start-up, `x \in Real`, `/` and `Infinity` fail when
  evaluated), nor are the temporal quantifiers `\EE` / `\AA`, nor a few `INSTANCE` corner cases
  (references to declarations through nested parameterized instances, operator-valued instance
  parameters). PlusCal is not translated: tlx checks the TLA+ translation that is in the file.
- **Sets whose size overflows TLC's int**: `Cardinality` (TLC's `Value.size`) refuses `SUBSET S`
  with `|S| >= 31` and a `[S -> T]`, `\X` or record set whose product of component sizes does not
  fit an int ([tlc-semantics.md](tlc-semantics.md) section 4). Enumeration itself needs no size:
  tlx streams a single bound's domain and `x' \in S`, and TLC streams `x' \in S`, `{x \in S : P}`
  and printing (the default order) for every set type. A *bound* asks for the normalized order,
  which TLC implements by materializing everything but `SUBSET S`, an enumerated set and
  `kSubset(k, S)`, so a `SUBSET S` domain agrees — `\E s \in SUBSET (1..31) : s = {}` is TRUE in
  both — while a
  `[S -> T]`, `\X`, record or interval domain whose materialization is larger than TLC's
  `-maxSetSize` (default 10^6) is an error in TLC ("too many elements") and keeps computing in tlx
  ([features.md](features.md) section 1 records that tlx does not implement that bound). This
  difference is in tlx's quantifier bounds over those domains, not in `x' \in S` or filtering.
- **Sets kept as a whole**: `CHOOSE x \in S`, `x' \subseteq S` and a bound of several variables
  (`\E x, y \in S`) refuse such a set in tlx, where TLC streams a `SUBSET S` or enumerated domain
  and answers: `CHOOSE s \in SUBSET (1..31) : s = {}` is `{}` in TLC, and `x' \subseteq S`
  enumerates the subsets; for the other set types TLC materializes as above.
- **Command line** (outside the contract, section 2): TLC's `-continue`, `-difftrace`,
  `-maxSetSize`, `-fp`, `-lncheck`, `-terse` and others are not implemented and give a usage error
  (exit code 2); `-cleanup` and `-noGenerateSpecTE` are accepted without effect; no `*_TTrace_*`
  files are written. Implemented with limits: `-coverage` is action-level only (D-12), `-checkpoint`
  works only at BFS level boundaries and `-recover` accepts only checkpoints written by the same tlx
  binary (D-16). Item by item in [features.md](features.md) section 1.
- **Memory**: liveness is checked offline after the search and needs extra memory for the
  behavior graph; beyond `-maxmem` tlx reports `liveness needs more memory` (a system error, exit
  code 255). With `-fpmem` the fingerprint set has a fixed size and a full table is a capacity
  error (it does not enter the disk tier).
- **Compiled tier** (results are not affected): there is a long tail of coverage (VIEW together
  with SYMMETRY still computes fingerprints on values; the remaining boxed nodes are in
  [design.md](design.md) section 6.8); a layout miss in simulation restarts the whole simulation from
  scratch with the same seed (side effects accounted for as in design.md section 6.5.3); a small model
  uses the result of the faithful pre-run only when that pre-run exhausts the state space
  ([design.md](design.md) section 6.5.1), a non-faithful pre-run that exhausts it still leads to compilation.
- **Runtime** (results are not affected): NUMA sharding is not done ([design.md](design.md)
  section 7.7); with oversubscription a descheduled worker still holds the block it claimed and the
  level barrier waits for it.
- **Output** (outside the contract, section 2): the wording of some evaluation errors differs from
  TLC's; the nested-expressions call stack of `-tool` message 2103, the message text and location
  suffix of general evaluation errors are not reproduced; the extra behaviors TLC's simulator
  produces through thread races after an error are not reproduced.
- **Front end**: acceptance/rejection agrees with SANY on the corpus (0 differences,
  [design.md](design.md) section 3.2); SANY defects intentionally not copied: D-17.
